# 仓库体系与压力分担

## 总览

九个数据仓库按压力的类型分为三组，每组三个仓库。每组覆盖一个方向的两端，中间由日志驱动串联。

```
                journal（日志）——驱动整个循环
                ┌─────────────────────────────┐
                │                             │
   intention    │  insight    │  roadmap      │
   （意图）      │  （洞察）    │  （蓝图）       │  ← 方向压力
                │                             │
   ──────────── │ ─────────────────────────── │
                │                             │
   journal      │  profile    │  brochure     │
   （日志）      │  （简介）    │  （宣传册）     │  ← 执行+不确定压力
                │                             │
   ──────────── │ ─────────────────────────── │
                │                             │
   history      │  library    │  report       │
   （历史）      │  （图书馆）  │  （报告）       │  ← 回顾+认同压力
                │                             │
                └─────────────────────────────┘
                              │
                          AI 执行层
```

---

## 第一组：意图·洞察·蓝图 —— 方向压力

这组回答"往哪走"。压力源是方向不明确、边界不清楚、判断没依据。

### intention（意图）

**回答的问题：** 为什么做？什么不做？

具体的压力场景：
- 同时有多个方向可选，不知道该聚焦哪个
- 做着做着发现越做越多，不知道什么该停下来
- 别人提了一个需求，不确定是不是该接

**内容特征：** 陈述型的"不做"比"要做"更重要。明确当前阶段什么不该操心，比列一堆"要做"更能减轻压力。每一句"我们不做X"都是帮人类省掉一次纠结。

**维护方式：** 遇到需要决策的事，先问"这事在我们的意图范围内吗？"不在就放下，在就进入下一步。

### insight（洞察）

**回答的问题：** 看到了什么？怎么判断？

具体的压力场景：
- 遇到了一个没处理过的问题，不知道怎么分析
- 做过类似的事但记不清当时的判断依据了
- 需要判断一个方案的好坏，但标准不明确

**内容特征：** 记录的是判断逻辑，不是结论。"当时为什么这么判断"比"当时的结论是什么"更有复用价值。结论会过时，判断逻辑不会。

**维护方式：** 做完一件事后，把"我发现了什么规律"写在这里。不需要长篇大论，关键是把隐性判断显性化。

### roadmap（蓝图）

**回答的问题：** 去哪里？先去哪再去哪？

具体的压力场景：
- 知道要做什么但不知道从哪开始
- 事情太多排不出优先级
- 做到一半不知道下一步该做什么

**内容特征：** 可执行的步骤链。每一步都应该是"明天可以开始做的事"，而不是"希望有一天实现的目标"。蓝图拆得越细，执行的阻力越小。

**维护方式：** 把目标拆成可以在 1-2 天内完成的步骤。完成一步就划掉一步，划掉的动作本身就在释放压力。

## 第二组：日志·简介·宣传册 —— 执行与不确定压力

这组回答"从哪出发"。压力源是事情太多做不完、外部变化太快、信息不一致。

### journal（日志）

**回答的问题：** 当前在做什么？在想什么？

具体的压力场景：
- 脑子里想法太多，记不住
- 一天结束了不记得自己干了什么
- 有一个想法但不成熟，不知道要不要跟进

**内容特征：** 零门槛的原始记录。不需要结构化，不需要完整，不需要对谁负责。日志的价值在于"记下来"，不在于"记得好"。日志是整个体系的驱动点——想法从这里产生，被分类后分流到其他仓库。

**维护方式：** 有想法就记，不评判好坏。定期回顾，把有持续价值的内容提炼到对应的仓库。

### profile（简介）

**回答的问题：** 当前是什么状态？有什么事实依据？

具体的压力场景：
- 有人问"这个业务的现状是什么样的"，答不上来
- 做了一个决策但依据是什么说不清
- 同一个事情不同的人说出来的版本不一样

**内容特征：** 当前状态的事实快照。应该包含可验证的数据和明确的定义。不确定性往往来自信息缺失——profile 就是消除信息缺失的工具。

**维护方式：** 以数据（JSON/YAML）为主，减少模糊描述。关键数据定期更新，过时的信息及时清理。

### brochure（宣传册）

**回答的问题：** 对外怎么说？

具体的压力场景：
- 客户问"你们是做什么的"，不知道怎么简单说清楚
- 对外宣传的内容和内部实际情况不一致
- 不同渠道说出来的口径不统一

**内容特征：** 对外版本的事实和故事。和 profile 的不同在于：profile 是对内的全部事实，brochure 是对外的精选事实。不造假，但选择和排序是可以调整的。

**维护方式：** profile 更新后检查 brochure 是否需要同步。对外口径变化时先改这里，再通知所有人。

## 第三组：历史·图书馆·报告 —— 回顾与认同压力

这组回答"走过什么路"。压力源是不确定自己做对了没有、不知道怎么向别人证明、怕重复踩坑。

### history（历史）

**回答的问题：** 走过什么路？踩过什么坑？

具体的压力场景：
- 以前犯过的错误，现在又犯了一次
- 新来的同事问"这个项目以前是怎么做的"，没人说得清
- 做决策时总感觉"好像以前遇到过类似情况"

**内容特征：** 关键事件的时间线 + 经验教训。不记流水账，只记"值得记住的事"。判断标准是：如果这件事以后可能有用，就记。不确定的话也记。

**维护方式：** 定期（每周或每月）回顾日志，把有长期价值的事件提炼到这里。

### library（图书馆）

**回答的问题：** 外部参考了什么？有什么依据？

具体的压力场景：
- 做一个方案但不知道业界是怎么做的
- 需要引用外部资料支撑自己的判断
- 感觉自己闭门造车，不知道外面有没有更好的做法

**内容特征：** 外部资料的索引和提炼。不是原文搬运，而是"这篇文章的核心观点是什么、对我们有什么启发"。图书馆的价值不在于收藏了多少资料，在于有多少资料被引用过。

**维护方式：** 读到好东西就记到这里，写清楚"为什么这个值得记"。

### report（报告）

**回答的问题：** 做得怎么样？有什么成果？

具体的压力场景：
- 月底了要写总结但不知道写了什么
- 需要向别人证明工作成果但拿不出数据
- 感觉做了很多但说不清楚到底做成了什么

**内容特征：** 结构化的事实汇总。包含数据、趋势、对比。报告的本质是"把 journal 里的原始记录加工成可对外或对上级交代的版本"。

**维护方式：** 定期（每日/每周）从 journal 和 profile 提取数据，生成结构化报告。自动化生成优于手动写。

## 三组之间的流转关系

```
journal（日志）——所有想法的入口
    │
    ├──→ 日常执行 → profile（简介）更新当前状态
    │
    ├──→ 发现问题 → intention（意图）调整边界
    │              → insight（洞察）记录判断
    │              → roadmap（蓝图）新增步骤
    │
    ├──→ 完成事项 → report（报告）生成总结
    │              → history（历史）沉淀经验
    │
    ├──→ 外部参考 → library（图书馆）收录资料
    │
    └──→ 对外输出 → brochure（宣传册）统一口径
```

压力不是被"解决"的，是被这个系统分流了。每一组承接一部分压力，剩下的交给下一组或者交给 AI。日志是驱动点，AI 是执行层。

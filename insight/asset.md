# 数字资产洞察

## 资产模块的命令结构

CLI 的 `asset` 模块经过多次迭代后，最终确定了三个子命令的边界：

| 命令 | 功能 | 性质 |
|------|------|------|
| `archive` | 将 journal 日志归档到 archive | 操作 |
| `status` | 结构合规检查（文件/格式/提交规范） | pass/fail |
| `quality` | 语义质量评估（叙事/知识/认知三维度） | 评分 |

这个边界不是一开始就清楚的。经历了 `audit` / `evaluate` / `quality` / `status` 四个命名的反复修改才最终定型。

## 命名的演变过程

1. `backup` → `archive`：备份改归档，更准确描述行为
2. `audit` → `status` + `quality`：审计拆分为结构合规（status）和语义质量（quality）
3. `evaluate` → 合并入 `quality`：评估功能统一到质量命令

核心教训：当两个概念不清楚的时候，往往不是命名问题，而是问题本身就站在多个领域的交叉点上。

## 质量评估的三维度框架

质量评估从实验室（Python 脚本）移植到 CLI（Rust），最终评估标准以 JSON 定义在 profile 仓库：

| 维度 | 指标数 | 核心问题 |
|------|--------|---------|
| 叙事工程 | 1 | 文档是否清晰易懂 |
| 知识工程 | 5 | 知识是否可编程（条件/参数/流程/角色/校验） |
| 认知工程 | 1 | 是否包含意图→流程→验收三段论 |

评估标准存放在 `profile/asset/quality.json`，CLI 运行时从 profile 加载，不需要重新编译。

## 以 profile 为事实源

分类规则和质量评估标准都从 `data/profile/` 加载，CLI 不再硬编码业务数据。加载链：

```
环境变量 → TOML 配置 → profile JSON → 硬编码 fallback
```

统一的环境变量 `QTRECURIT_PROFILE` 指向 profile 仓库路径。

## 领域交叉的本质

数字资产审计天然跨了四个领域：数字资产管理、叙事工程、知识工程、认知工程。这不是一个"纯"资产领域的问题。在处理这类交叉领域的 CLI 命令时，与其试图把所有逻辑塞进一个命令，不如明确这个命令站在哪个领域里，然后把其他领域的内容以数据（profile）的形式引用。
